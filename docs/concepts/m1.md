## Object identity and aspects
Created: 2026-10-11
Modified: 2026-10-11

M1 has one structural primitive: the entity, identified by a stable identifier. All meaning, structure, and relationships are expressed through attached aspects. The core specification permits entity identifiers to be UUIDs or tag URIs; Lion's stated plan for Arcs uses UUIDs for arc objects. An entity's chosen identifier is permanent.

An aspect is an identified value attached to a particular entity. Its identifier determines the dimension of meaning and the expected interpretation of its content; that identifier can be shared across entities. The core does not require a separate UUID for each attachment. Aspect identifiers should be entity IDs, with tag URIs recommended. Content may be any valid JSON value, not just an object. Presence with null content still asserts the aspect; absence means its identifier is absent from the applicable entity-aspect mapping.

UUIDs must use the standard hyphenated form and be normalized to lowercase before storage, comparison, or emission. Tag URIs must be preserved exactly, with exact string equality; do not lowercase or otherwise normalize them. Lion confirmed that “taguries” was a dictation error for **tag URIs**; normalize that transcription in prose, not the identifier strings themselves.

## Basic Aspect
Created: 2026-10-11
Modified: 2026-10-11

The Basic Aspect, `tag:m1lattice.net,2026:aspect/basic`, is common rather than structurally exceptional. Its optional fields are `typehint`, `name`, `title`, `description`, `tags`, `url`, `file`, `image`, `date`, `location`, `notes`, and `hook`; additional keys are allowed. A **hook** is a brief conceptual cue that draws attention to why something matters. `name` is a compact program-friendly label, while `title` is suitable for human-facing display.

Basic fields are loosely interpreted and non-authoritative. Precise structure belongs in specialized aspects. In particular, Basic's general-purpose `date` does not define an arc's beginning and end or an event's moment. `file` and `image` are resource references: entity IDs resolved through tables are recommended, while direct paths and URLs are permitted. `typehint` is an informal indication, not authoritative typing.

## Links and extensibility
Created: 2026-10-11
Modified: 2026-10-11

Links are entities with their own identities, recognized by the conventional Link Aspect, `tag:m1lattice.net,2026:aspect/link`. Its content requires `from` and `to` entity IDs, and optionally includes `type` (an entity ID describing the relationship type) and `typehint` (a human-readable relationship label). Additional keys and aspects are allowed, and multiple links may connect the same pair of entities.

[Arcs](arc.md) will use this model conceptually for transitions, containment, dependencies, and other relationships. The generic link structure is now known; the particular relationship identifiers and specialized Arcs aspects remain undecided. Because links are entities, they can themselves carry descriptions and other aspects.

## Resolution tables and scope
Created: 2026-10-11
Modified: 2026-10-11

M1 resolution tables map entity IDs to zero or more resource locations. They are environment-specific infrastructure outside the core ontology, permit multiple locations, and leave location selection to consuming applications. The specified shape maps identifiers to arrays of location objects, such as objects with `type: file` and `path`, or `type: url` and `url`.

Our `db/file-system-locations.json` is a project reference list with registry document IDs; it has not been defined as an M1-compliant resolution table.

Core defines the conceptual model, not memory or storage representation. Transport, deletion, tombstones, layering, priority, and contribution-merging semantics are outside its scope. Reading core alone does not settle those implementation questions.

## Arcs interoperability requirement
Created: 2026-10-11
Modified: 2026-10-11

Lion explicitly clarified that Arcs may structure and store its data however it needs: SQLite databases, custom JSON formats, or other representations are all available choices. The requirement is conceptual mappability to M1 so Arcs can cooperate with other systems. Stable UUID identity is the key. This does not require native M1 storage, an aspect-shaped internal schema, or choosing a storage format now. Any mapping must preserve the identities of the objects being represented.

## Simplified M1 kernel in Arcs
Created: 2026-10-11
Modified: 2026-10-11

Arcs uses a **kernel of M1**, or **simplified form**, rather than a literal full M1 representation internally. What matters is that existing structures can be expanded into full M1 representations if needed, preserving stable UUID identity, content, and relationship meaning. Formal field names, aspect envelopes, and tag URI encodings need not be carried everywhere in the internal model. This is a project description, not a separate standardized M1 profile.

For example, Basic has one simplified `type` field for object kind (`arc`, `event`, `journal-entry`, or `link` when optional Basic metadata describes a link); it can map to formal Basic's `typehint`. Links have their own UUIDs and a separate `type` for relationship kind. Short strings such as `transition`, `via`, `member-of`, and `parent-child` map to the formal identifiers in [M1 link types](../design-references/m1-link-types.md). A link does not require a Basic row to remain an identified entity mappable to a formal Link Aspect.

Use the simplified model deliberately and document its expansion mappings. Do not introduce internal complexity solely to imitate the formal representation, or discard information and identity needed for a faithful later expansion. The descriptions of formal M1 elsewhere in this note explain the target model; they do not override the application's simplified storage decisions.

## Log Aspect and domain records
Created: 2026-10-11
Modified: 2026-10-11

The Log Aspect, `tag:m1lattice.net,2026:aspect/log`, contains a chronological `log` array. Entries require a UTC `timestamp` and an `event` code, and can include `note`, `agent`, and `via`. Entries should be appended and preserved; identical duplicates must be eliminated during merging. Suggested codes include CREATED, UPDATED, ACCESSED, DEPRECATED, and NOTE. CREATED means creation as M1 data, not the beginning of the real-life passage an entity represents.

This convention does not establish that Arcs' [events](event.md) or [journal entries](journal-entry.md) are Log Aspect entries. Their representation remains a separate design question, especially where a single record is associated with multiple arcs.
